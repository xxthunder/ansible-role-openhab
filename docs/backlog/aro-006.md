# [ARO-006] Keep the permission tasks stable against openHAB's own writes

**Status**: Open
**Priority**: Low
**Component**: `tasks/main.yml`
**Related**: [ARO-002](aro-002.md) — its release check on a real host found
this; HSH-057c in the consuming project, where it showed.

**Summary**:
As the role maintainer, I want a second run to report `changed=0` whatever
openHAB wrote in between, so that a change in the recap always means the host
changed.

**Description**:
"Create if necessary and set the permissions on the openHAB data folder" resets
every file under `openhab_home` to `u=rwX,g=rwX,o=`, recursively. Whenever
openHAB saves a jsondb file it writes a backup to `userdata/jsondb/backup/`, mode
0644, and keeps the last five; a binding that refreshes its session saves
often. So a run shortly after another reports `changed` for re-chmodding those
backups — found 2026-10-20 on a real host: five files, nothing else in the
tree. It is harmless, since every directory of the tree is 0770 and the files'
`o+r` reaches nobody, but it keeps the recap from ever being clean, and the
task walks all of `userdata/` on every run.

The group-write part is load-bearing: it is what lets the operator, a member of
the service account's group, edit `conf/` and run git in both trees. So the
fix is to narrow the `mode`, not to drop it:

- ownership recursively over the whole tree — openHAB writes as the service
  account, so that stays stable;
- `u=rwX,g=rwX,o=` recursively only where the operator works: `conf/` and
  each tree's `.git`;
- `0770` on `openhab_home` and the directories the container mounts, not
  recursively.

"Change ownership of the openHAB tree" then goes: it walks the tree a second
time to set what the first task already set.

**Acceptance Criteria**:
- [ ] A second run reports `changed=0` while openHAB keeps writing — checked on
      a real host, the way this was found.
- [ ] The operator, as a member of the service account's group, can still edit
      files in `conf/` and commit and push in both trees.
- [ ] Nothing under `openhab_home` is reachable for users outside that group.
- [ ] A run walks the tree recursively at most once.
- [ ] Released RC-first, like ARO-002.

**Out of scope**:
- openHAB's own umask or ACL defaults — the fix stays in the role.
