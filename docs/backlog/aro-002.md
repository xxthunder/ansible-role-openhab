# [ARO-002] ✅ DONE - Seed `conf/` and `userdata/` from two repositories

**Status**: Done (2026-10-19)
**Priority**: High
**Component**: `tasks/git.yml` (new), `tasks/main.yml`, `defaults/main.yml`,
`molecule/git-seeding/` (new), `README.md`
**Related**: HSH-057c in the consuming repo — the parent-side wiring, the
migration runbook, and the pin bump.

**Summary**:
As the role maintainer, I want `conf/` and `userdata/` seeded from separate
repositories with opposite ownership, so that deploying declarative config can
never discard live runtime state.

**Description**:
`openhab_home` holds two things with opposite ownership. `conf/` is declarative
automation and the repo is its source of truth; `userdata/` is runtime state —
thing status, jsondb, user sessions, and secrets that rotate on their own — and
the host is its source of truth. A single `openhab_repo` forced them to share
one policy, and `openhab_repo_force` applied that policy to the whole tree, so
enabling it discarded runtime state on every deploy.

Both repos now only *seed* a target that is not yet seeded, and never fetch
again; a converged host sees only origin-URL upkeep, which cannot touch a
working tree. So no code path can reset a populated tree, the host needs no git
credential in steady state, and publishing new config stays a deliberate
operator step.

The two differ only in what counts as unseeded: `conf/` when it holds no `.git`,
`userdata/` when the directory itself is absent. That asymmetry is the safety
property — a `userdata/` present without a `.git` is a hand-built host holding
the only copy of its runtime state.

**Delivered before this repo had scaffolding.** The implementation landed as a
single commit on `hsh-057c-two-repos` while work was still being driven from the
consuming repo's session. It is not being redone; the RC tag is its verification
gate. What remains is proving it.

**Found by the first run** (2026-10-18, in CI): the `[safe]` block in
`/root/.gitconfig` used one fixed marker, so a second `openhab_home` on the
same host overwrote the first one's entries on every run — not idempotent. The
marker now carries `openhab_home`. The scenario's `prepare` also never created
the pre-seeded `userdata/` directory; it had simply never run.

**Found by review** (2026-10-19); the scenario now pins all but the last:
- The guard on `openhab_repo` returned the variable, not a boolean. ansible-core
  2.19+ rejects that, so a set `openhab_repo` failed with a templating error
  instead of the pointer, and a blank or null one failed a run that should pass.
- `safe.directory` was written after the first git command. On a host whose
  trees the service user owns, the URL upkeep died on "dubious ownership"
  before the block that would have allowed it, on every run. The scenario's
  pre-seeded trees are now service-owned, as on a real host.
- A seed that failed half-way left `conf/.git`, or `userdata/` itself, behind,
  and every later run took that for a seeded tree. A failed `conf/` seed now
  removes its `.git`; `userdata/` is built beside the target and moved into
  place last.
- The seeded branch tracked nothing and the fetch was shallow, so the manual
  `git pull` and `git push` failed and the state repo's rollback points were
  missing on the host.
- A seed had no way to authenticate: root holds no key by design, `become`
  strips an agent the operator forwards, and root had never seen the git
  server's host key. The seed now picks the forwarded agent up from the
  connecting user's session, records the host key on first contact, and never
  prompts. The scenario seeds over ssh with the only key in such an agent.
- URL upkeep reported a corrected remote as unchanged, and on `userdata/`
  swallowed every error. It now reads the URL first, reports a correction as a
  change, and is gated on `.git` for both trees.

**Found at the release candidate** (2026-10-19, the operator's `--check`
against the real host, rc3): check mode only pretends to write the `[safe]`
block, but the URL read runs for real, so on a host whose trees the service
user owns it died on "dubious ownership" before the first deploy. The role's
own git commands now pass `-c safe.directory` themselves, and the scenario
runs a check-mode converge before the first real one.
