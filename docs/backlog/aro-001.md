# [ARO-001] Scaffold the repo for standalone agentic development

**Status**: In Progress
**Priority**: High
**Component**: `AGENTS.md`, `.claude/settings.json`, `.githooks/commit-msg`,
`docs/backlog/`, `README.md`, `.devcontainer/` (new), `pyproject.toml` (new),
`uv.lock` (new), `scripts/test.sh` (new), `molecule/git-seeding/molecule.yml`
**Related**: `HSH-067` in the consuming project's backlog — the item that
requested this split and carries the parent-side follow-through. Cited by ID
only; see the backlog README on why cross-repo references are not links.
[ARO-002](aro-002.md) — carries `molecule/git-seeding`, so its branch must reach
`main` before molecule can be proven here; [ARO-004](aro-004.md) — consumes the
parity contract this item builds, and adds nothing to it but a workflow file.

**Summary**:
As the role maintainer, I want this repository to carry its own development
scaffolding and backlog, so that role work happens under its own discipline
rather than borrowing the consuming project's session and fighting its tooling.

**Description**:
Role work was previously done from the consuming project's session, which
fights the setup at every turn: the parent's `commit-msg` hook does not reach a
submodule, its `scripts/lint.sh` excludes submodules by design, its
`Bash(ansible*)` deny
entry makes `ansible-lint` unreachable, and its devcontainer has no Docker so
molecule cannot run. The role's own debt — a vestigial `molecule/default`, no
CI, no release tags — had outgrown a checkbox inside someone else's item.

The consuming project's `HSH-067` requested the split and recorded the decision
that this repo stays under `xxthunder` alone: the fork of
`fex01/ansible-openhab` is a permanent divergence, so the first tag starts a new
lineage rather than continuing the original author's.

The environment question this item left open is now settled. Development runs in
a devcontainer defined *here* and brought up as a DevPod workspace on the
consumer's Docker-capable dev host, rather than by installing a toolchain onto
that host. Two jobs were being asked of one thing and have been separated: the
**devcontainer** exists to give this repo a project root — its `AGENTS.md` loaded
as instructions, its `.claude/settings.json` deny list actually in force, its
hooks, its own context — none of which a lockfile provides. **Reproducibility of
the build** is a separate contract made of pinned files, and it is what makes a
run here and a run in CI the same run.

**Scope Decisions**:
- **The devcontainer runs on the consumer's dev host, which stays a pure Docker
  host — decided 2026-08-26.** That host's provisioning role states outright that
  the dev environment lives inside each workspace's `.devcontainer`, not on the
  host. Cloning this repo onto it and installing molecule there would work and
  would solve the project-root problem too, but it contradicts that model and
  does not generalise: six sibling role repos have identical needs, and a
  devcontainer is copied where a host toolchain is re-installed and drifts.
- **`docker-outside-of-docker`, not docker-in-docker.** dood mounts the host's
  Docker socket, so a container molecule creates is a *sibling* on the host's
  daemon — the same topology a GitHub-hosted runner has. dind runs a nested
  daemon whose containers are *children*, a shape no CI run ever has, and needs
  `--privileged`. dood also shares the host's image cache across every role
  workspace. Verified safe: neither `molecule/default` nor `molecule/git-seeding`
  declares a `volumes:` key, so dood's one weakness — the daemon resolving a
  bind-mount path against the *host* filesystem, silently mounting an empty
  directory — cannot arise. If a future scenario needs a bind mount, the fix is
  matching `workspaceMount`/`workspaceFolder` paths on both sides, not switching
  to dind.
- **The devcontainer is development-only; CI never builds it.** Parity comes from
  pinned files, not from a shared image. A GitHub runner has Docker natively, so
  it needs no nesting at all: `uv sync --frozen`, then the same entry point.
  Rejected: the `devcontainers/ci` action, which would give literal image parity
  at the cost of rebuilding the image on every run, to guarantee something the
  lockfile already guarantees.
- **`ansible-core`, never the `ansible` bundle.** The bundle ships ~50 vendor
  collection namespaces, installing a second copy of everything a
  `requirements.yml` pins and leaving search-order precedence to decide which
  copy wins. The consumer hit exactly this and fixed it in `HSH-068`; this repo
  starts on the right side of it rather than retrofitting.
- **The parity contract belongs here, not in ARO-004.** The lockfile and the
  pinned platform image are what make the devcontainer worth having — without
  them the workspace is reproducible in shape but not in versions. ARO-004 is
  reduced to a workflow file that calls `scripts/test.sh`.

**Sequencing**: `molecule/git-seeding` exists only on ARO-002's branch. It must
reach `main` before "prove molecule runs" means anything here, and before this
branch's `AGENTS.md` stops describing a scenario that is not on `main`.

**Acceptance Criteria**:
- [x] `AGENTS.md` documents the role's conventions, the submodule-pin
      consequence, testing, and the RC-first release process.
- [x] `.claude/settings.json` denies playbook execution against real
      infrastructure while deliberately leaving `ansible-lint` available.
- [x] `.githooks/commit-msg` enforces conventional commits with an `ARO-###`
      reference; installing it is documented.
- [x] `docs/backlog/` bootstrapped with the `ARO-` prefix and an index.
- [x] `README.md` states the permanent divergence from `fex01/ansible-openhab`.
- [x] The known debt is filed here rather than upstream: ARO-003, ARO-004,
      ARO-005 exist and the consumer's backlog carries no role internals.
- [ ] `.devcontainer/` exists: a Debian/Python base with uv, the
      `docker-outside-of-docker` feature, and a `postCreate` that runs
      `uv sync --frozen`, sets `core.hooksPath` to `.githooks`, and installs
      Claude Code.
- [ ] The devcontainer is role-generic — nothing openHAB-specific in it — so a
      sibling role repo can adopt it by copying the directory.
- [x] `pyproject.toml` and `uv.lock` pin the toolchain: `ansible-core`,
      `molecule`, `molecule-plugins[docker]`, `ansible-lint`, `yamllint`. The
      `ansible` bundle appears nowhere.
- [ ] Collections used by scenarios are pinned in `molecule/*/requirements.yml`.
- [x] The molecule platform image is pinned to a tag or digest —
      `docker.io/pycontribs/debian:latest` is a moving target and today's
      largest parity hole.
- [x] `scripts/test.sh` is the single entry point. No other command for running
      the suite appears in `AGENTS.md`, `README.md`, or a workflow.
- [ ] Molecule is proven runnable from this project's workflow —
      `molecule test -s git-seeding` completes inside the workspace.
- [ ] `AGENTS.md`'s Testing section reflects the new workflow. It currently
      tells the reader to run scenarios on a Docker-capable host *because the
      consumer's devcontainer has no Docker*; that stops being the reason and
      stops being the instruction.
- [ ] An ADR records the environment decision — dood over dind, and the
      devcontainer being development-only — with the reasoning, not just the
      outcome.
